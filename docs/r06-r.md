# R06-R — R5 implementation review and remediation

**Review date:** 2026-09-15.  
**Status:** review documented; remediation and remaining hardware acceptance **open**.  
**Reviewed source version:** `0.11.30-arch-r9c`, from [`src/web_http.h`](../firmware/src/web_http.h#L13-L16). Devices were not queried during this review.

R06-R is the requested identifier for this **review of R5's current implementation**, including later R6/R9 changes where they affect R5 guarantees. It does not rename R5 or replace the R6 pair-operation checkpoint. Publication is documentation-only: none of the repairs below has been implemented by this review, and this document does not authorize flashing or disruptive hardware checks.

## Decision and scope

**The portable pairing core substantially follows the agreed architecture, but the current integration should not receive an unqualified R5 sign-off.** The highest-priority defects are in diagnostic UART ownership, stored-selection loading/migration and fault isolation around that core. Passing core tests do not establish that these service boundaries work.

Requirements are taken from the [architecture plan's pairing and selected-link contracts](architecture-review.md#pairing-startup-and-selected-link-independence), [persistence and recovery contracts](architecture-review.md#pair-wide-selection-persistence-and-failure-handling), [automatic-test contracts](architecture-review.md#one-button-link-tests-countdown-and-durable-results), and [R5–R6 execution steps](architecture-review.md#r5r6--remove-manual-pairing-and-make-switching-recoverable). Historical deployment evidence remains in the [R5 record](../tests/2026-09-15-arch-r5/README.md); later [R6](../tests/2026-09-15-arch-r6/README.md), [R9a](../tests/2026-09-15-arch-r9a/README.md) and [R9b](../tests/2026-09-15-arch-r9b/README.md) records are not rewritten by this review.

Scope excludes redesigning survey storage, changing receiver quality thresholds, adding RF authentication, or finishing unrelated R10 extraction work. Unit IDs, CRC and challenge echoes provide isolation/freshness, **not cryptographic authentication**; the agreed design explicitly makes that distinction.

## Findings and recommended repairs

### F01 — Release diagnostic UART ownership through a complete, bounded handoff

**Sources:** [`link_diagnostic.cpp:357–386`](../firmware/src/link_diagnostic.cpp#L357-L386), [`link_service.cpp:199–207`](../firmware/src/link_service.cpp#L199-L207), [`link_service.cpp:424–437`](../firmware/src/link_service.cpp#L424-L437), [`correction_pair_test.h:56–84`](../firmware/src/correction_pair_test.h#L56-L84).

`radio_reserved` is calculated from nonzero `pair_engine.run` or `engine.config.run`. Both engines retain their run IDs after completion or cancellation. Diagnostic busy state becomes false, but the link service still refuses Radio TX and skips its Radio RX loop. The diagnostic layer continues consuming UART2 input into the terminal engine.

It prevents automatic Radio bootstrap, heartbeats, correction traffic and OTA peer notices from resuming. A later cutover to Radio through the pair-operation (Settings) path cannot negotiate either, because its staging engine shares the same reserved stream; only the local diagnostic correction-selection path clears the retained run markers today, and normal recovery must not depend on that extra operator step.

**Observed off-target:**

```text
Completed clean Radio test: pair_pass=1 busy=0 retained_run=123456 radio_reserved=1
Five minutes later: next_test_packet=0 busy=0 radio_reserved=1
Cancelled Radio test, five minutes later: busy=0 retained_run=123457 radio_reserved=1
```

**Recommended repair:** separate the saved report from active transport ownership. Reserve UART2 through the required, bounded terminal result exchange, then stop diagnostic RX/TX and hand the stream back completely in one main-loop transition. Completion, cancellation and peer disappearance must all converge on that finite handoff and the agreed production-restoration path.

Do **not** fix only the reservation predicate by changing it to `busy()`: terminal RTC1 result exchange still uses UART2, and the diagnostic receive loop must stop draining the stream too. Follow the plan's bounded peer-result exchange/restoration contract rather than making the existing 60-second engine retransmission window an indefinite reservation.

**Acceptance:** successful, failed, cancelled and peer-missing Radio tests all release the stream within the declared bounds; reports remain downloadable; automatic Radio pairing, real correction forwarding when eligible, and OTA notices resume without local reselection or reboot. Exercise both Radio-selected and Wi-Fi-selected starting states, with no simultaneous stream consumers and no synthetic output to UM980.

### F02 — Fail closed on invalid records and publish one validated migration baseline

**Sources:** [`link_service.cpp:64–110`](../firmware/src/link_service.cpp#L64-L110), [`link_service.cpp:345–351`](../firmware/src/link_service.cpp#L345-L351), [`link_operation.cpp:61–77`](../firmware/src/link_operation.cpp#L61-L77), [`link_operation.cpp:134–143`](../firmware/src/link_operation.cpp#L134-L143).

There are two repair increments within this finding.

**F02a — Corruption and absence are conflated.** A wrong-length `confirmed` record takes the missing-record path. An invalid legacy `selection` record is also ignored. Either can leave `ok=true` and silently choose Wi-Fi or a legacy value. Independently, validation of `pending` overwrites the earlier `confirmed` validation result, allowing a valid pending record to hide a corrupt confirmed record. A truncated pending marker is treated as absent.

**F02b — Valid R5 Radio migration diverges between owners.** The legacy branch writes the selected medium into a default-constructed `Confirmed` without sealing it. `link_service::begin` adopts the raw Radio transport, while `link_operation::Engine::begin` rejects the invalid new-format record and retains its Wi-Fi baseline. The actual production medium and the operation engine's selection/restoration baseline disagree.

**Observed with injected host storage:**

```text
Missing record (expected historical Wi-Fi default): load_ok=1 selected=wifi pending_tag=0
Valid R5 radio preference: load_ok=1 selected=radio pending_tag=0
CRC-corrupt R5 radio preference: load_ok=1 selected=wifi pending_tag=0
Truncated current radio preference: load_ok=1 selected=wifi pending_tag=0
Corrupt confirmed plus valid pending: load_ok=1 selected=wifi pending_tag=123
Truncated pending marker: load_ok=1 selected=radio pending_tag=0
Valid R5 Radio upgrade: production_transport=radio operation_baseline=wifi migrated_record_valid=0
```

These are controlled host injections, **not evidence that either deployed unit currently has corrupt storage**. The legacy `selection` format is R5, not R4.

**Recommended repair:** distinguish a genuinely absent key from a present unreadable, wrong-length or invalid record. Accumulate all validation failures; never let a later successful read erase an earlier failure. Validate the legacy record, construct and seal the new record, perform the checked migration write/readback, and only then expose a consistent baseline to both owners. Any indeterminate migration must report recovery rather than silently select a medium. Preserve unrelated NVS namespaces and survey data.

**Acceptance:** missing-record upgrade alone retains the historical Wi-Fi default; present corrupt, truncated, oversized or unreadable records yield `recovery_required` with production inhibited. A valid pending record cannot hide confirmed-record corruption. Valid Wi-Fi and Radio migrations give production and operation owners the same medium/revision before the first operation; failure/cancellation restores the actual confirmed medium. Migration write/readback failures remain explicit.

### F03 — Keep Radio faults local to Radio and reset them only at an explicit recovery boundary

**Sources:** [`correction_bridge.h:12–21`](../firmware/src/correction_bridge.h#L12-L21), [`link_service.cpp:129–148`](../firmware/src/link_service.cpp#L129-L148), [`link_service.cpp:356–365`](../firmware/src/link_service.cpp#L356-L365).

`Bridge::stop()` leaves `fault_` set. The service's snapshot applies that Radio fault regardless of the selected transport, and Wi-Fi setup does not call the Radio `Bridge::begin()` that clears it. After a Radio fault, an explicitly selected Wi-Fi pair can negotiate successfully while service-level connectivity, correction admission and peer notices remain blocked.

**Observed off-target:**

```text
Radio fault followed by Wi-Fi restart: core_connected=1 service_connected=0 service_reason=radio_output_fault
```

**Recommended repair:** scope Radio fault interpretation to the selected Radio path and reset the relevant bridge fault during an explicit teardown/recovery transition. Keep fault counters useful for diagnosis. Do not clear a short-write latch merely because another heartbeat arrives in the unchanged Radio session, and do not add automatic Wi-Fi fallback.

**Acceptance:** a short write continues to inhibit the current Radio session; explicit Wi-Fi recovery can establish a usable pair and carry eligible corrections/notices; explicit Radio recovery starts from a clean, proved session. An unselected Radio candidate fault must not poison healthy Wi-Fi production.

### F04 — Bind control admission to the adapter that received the envelope

**Sources:** [`link_service.cpp:166–197`](../firmware/src/link_service.cpp#L166-L197), [`link_service.cpp:414–432`](../firmware/src/link_service.cpp#L414-L432), [`pair_session.cpp:83–89`](../firmware/src/pair_session.cpp#L83-L89).

Wi-Fi and Radio call `route_control()` without an explicit ingress medium. Dispatch and pairing therefore rely on the envelope's self-declared transport. A correctly formed Radio-tagged PLC1 exchange fed through the Wi-Fi-address control path can establish Radio-configured engines.

**Observed off-target:**

```text
Radio PLC1 fed through Wi-Fi control ingress: Base connected=1 Rover connected=1 same_session=1
```

This is a cross-medium admission defect demonstrated by injection/relaying. It is **not** evidence that normal production transmit code secretly falls back to Wi-Fi. It also does not change the agreed non-cryptographic RF threat model.

**Recommended repair:** carry an explicit ingress transport from each adapter into control dispatch. Validate the declared transport against it before pair, staging or operation processing. Restrict session-bound notices and legacy classification to their actual selected/operation medium. Passive listeners remain allowed; an unselected listener cannot prove the selected path.

**Acceptance:** both cross-medium directions reject otherwise valid envelopes without advancing pair freshness, staging or operation state. Correct same-medium bootstrap, candidate operations and OTA notices still work. No Radio handshake succeeds because its messages were relayed over Wi-Fi.

### F05 — Complete the automatic diagnostic workflow cutover

**Sources:** [`diagnostics.html:18–29`](../firmware/web/diagnostics.html#L18-L29), [`diagnostics.html:42–74`](../firmware/web/diagnostics.html#L42-L74), [`run_sik_bench.py:74–87`](../firmware/test/run_sik_bench.py#L74-L87), [`check_diagnostic_hardware.cjs`](../firmware/test/check_diagnostic_hardware.cjs), [`check_correction_pair.cjs`](../firmware/test/check_correction_pair.cjs).

Live correction-session entry is gone, but Diagnostics still exposes a six-digit test code, separate per-instrument arming, matched profiles and instructions to arm both instruments. The page also retains the old Radio-test prerequisite to select Wi-Fi first. Remaining drivers coordinate the two devices themselves rather than requesting one device-owned operation.

The [R5 record](../tests/2026-09-15-arch-r5/README.md#L11-L11) explicitly deferred automatic synthetic tests to R9. The current Settings quick-test path does not remove the old matching workflow from advanced diagnostics. The agreed plan permits internal six-digit IDs, not operator-entered matching fields.

**Recommended repair:** route advanced starts/cancels through the same device-owned coordinator/reservation lifecycle, preserve supported engines/profiles/reports, and remove manual matching fields and two-device orchestration from callers. Do not replace advanced functionality with the narrower quick-test profile. Keep local recovery selection available under its explicitly labelled recovery semantics, rather than presenting it as normal pair coordination.

Update the [living correction guide](live-correction-bridge.md#select-the-correction-route), whose normal instructions still lead with two local selections and describe Settings as not yet shipped. Historical dated test records remain historical.

**Acceptance:** one current controller on either role can start the requested supported advanced test without sharing a number, opening the companion's HTTP page or first switching to Wi-Fi. Phase/result correlation, cancellation, bounded restoration and controller authorization remain intact. UI and drivers consume the same coordinator contract; reports and advanced profiles are retained.

### F06 — Bound stale-candidate interference without weakening current-boot proof

**Source:** [`pair_session.cpp:103–132`](../firmware/src/pair_session.cpp#L103-L132).

An unproved candidate from a dead peer boot can occupy the Base's single candidate slot until the 20-second expiry. Hellos from the actual new boot are refused while that slot is occupied.

**Reproduced scenario:** capture an untargeted Hello from a dead Rover boot; deliver it to an idle Base; then run a fresh Rover boot normally. Both production engines became connected after **21,250 ms**. Output remained inhibited until proof completed.

This is a **P3 bounded liveness improvement**, not a proven-session safety break. The review did not substantiate an unqualified 40-second recovery claim; it is not part of this finding.

**Recommended repair:** improve bounded handling of competing unproved candidates while preserving the invariant that delayed Hellos cannot replace or repeatedly reset a proven session. Do not simply invalidate the active session on a different boot ID.

**Acceptance:** a delayed dead-boot Hello does not consume a full additional negotiation window before the live peer can prove itself; prior replay, token-retirement, same-role, reboot and outage-retention cases continue to hold. Include candidate-expiry timing boundaries in the reproduction.

### F07 — Classify recognized incompatible envelopes before the service discards them

**Sources:** [`peer_update.h:35–39`](../firmware/src/peer_update.h#L35-L39), [`pair_session.cpp:12–26`](../firmware/src/pair_session.cpp#L12-L26), [`link_service.cpp:166–180`](../firmware/src/link_service.cpp#L166-L180).

The core recognizes an otherwise valid outer RTM1 version-2 envelope as incompatible. The service first calls `peer_wire::control()`, which rejects any outer version other than 1, so the same packet never reaches that classification.

**Observed off-target:**

```text
Recognized RTM1 version 2 through service: negotiating
Same packet delivered directly to core: protocol_incompatible
```

**Recommended repair:** separate structurally valid envelope classification from supported-body admission so recognized incompatible traffic reaches the existing actionable status path without becoming accepted control or data. Apply the physical-medium/companion checks as well. Do not classify silence or unrelated unselected-medium traffic as proof of a companion version mismatch.

**Acceptance:** recognized incompatible traffic on the applicable path reports `protocol_incompatible`, with production inhibited; malformed/unknown traffic remains rejected; silence remains `peer_unreachable`. A replayed incompatible frame must not tear down a fresh proven session.

## Verification performed and its limits

The review ran **temporary host-only executables**, without firmware builds, flashing, device API access or hardware mutations:

- The existing production pair-session suite from [`pair_session_cases.cpp`](../firmware/test/pair_session_cases.cpp) passed: startup, lossy proof, codec/replay boundaries, reboot, role, outage retention and clock wrap.
- The existing pair/OTA service cases from [`peer_service_cases.h`](../firmware/test/peer_service_cases.h) passed for **Wi-Fi and Radio**, including notice loss/retry, reboot isolation, current-boot quality recovery and cancellation tombstones.
- Focused reproductions compiled production cores and selected unmodified service function bodies with host doubles for storage/address/composition dependencies. The outputs above are those observed during the review, not on-instrument measurements.
- F05 is based on the current page, handler and driver code; its full coordinated replacement was not implemented or exercised.

The existing [main host harness](../firmware/test/run_host_tests.py#L23-L44) replaces `link_service` with stubs. Its success cannot validate the actual service's UART lifecycle, NVS migration, ingress dispatch or cross-transport fault state. Add focused regression coverage at that real service boundary for each repair, using fake hardware adapters rather than replacing the state owner being checked. Preserve the existing core checks; do not substitute UI string assertions for transport/state outcomes.

## G01 — Remaining hardware acceptance gate

The [R5 outstanding list](../tests/2026-09-15-arch-r5/README.md#L40-L43) leaves the isolated-medium cold-boot matrix, hardware replay and idle role-change work open. Reviewed later records demonstrate runtime cutovers and other useful checks, but do not close the complete matrix below.

| Scenario | Required evidence before sign-off |
|---|---|
| Radio selected, inter-instrument Wi-Fi unavailable | Base-first, Rover-first and simultaneous cold boots establish a fresh bidirectional pair over SiK alone; no browser coordination, numeric entry or GNSS-time prerequisite. |
| Wi-Fi selected, radios unavailable | All boot orders establish the equivalent pair without a working radio dependency. |
| Restart only Base, restart only Rover, change roles while idle | Valid opposite roles establish a fresh current-boot session; old queued/replay/health state does not leak; same-role state is actionable; saved jobs and settings remain intact. |
| Delayed/replayed old boot, control and data; wrong identity/role; recognized incompatible traffic | Stale or incorrect traffic is rejected; unproved candidates do not replace a proven session; status distinguishes incompatible from unreachable; unsafe production stays inhibited. |
| Completed/cancelled tests and explicit recovery after a Radio fault | The corrected ownership/fault paths return to an actually usable selected link, with eligible real correction forwarding and OTA notices; a test verdict or a pair-connected flag alone is insufficient. |

Use the architecture plan's [hardware verification procedure](architecture-review.md#verification) and the [OTA operator guide](ota-operator-guide.md). Verify current unit identities, firmware, roles, boot IDs, addresses, profiles, selected transport and saved-data baseline before any future commands. Historical addresses/COM ports are not target authorization. Prepare radio unavailability safely with power off; never remove an antenna from a transmitting radio. Preserve the distinction between the nearby tablet AP and inter-instrument Wi-Fi availability.

Runtime Radio selection with Wi-Fi still available is **not** radio-only cold-start acceptance. Indoor pairing is **not** outdoor RTK/FIXED or receiver-recovery qualification; that remains a separate field gate.

## Recommended remediation sequence and closure

Each row is a proposed, separately verified increment, not completed work. Follow the project's validate-first rule rather than batching several unverified behavioral changes into one deployment.

| Order | Work | Completion evidence |
|---|---|---|
| 1 | F01: bounded diagnostic result exchange and complete UART handoff | Reproduce before repair; pass/failed/cancelled/peer-missing release and actual Radio recovery after repair. |
| 2 | F02a: fail-closed record loading | Absence distinguished from every invalid/read-failure case; invalid state cannot enable production. |
| 3 | F02b: validated R5 migration | Wi-Fi/Radio upgrade gives both owners the same baseline; checked persistence and restoration verified. |
| 4 | F03: selected-medium fault isolation | Radio latch remains safe; explicit Wi-Fi and Radio recovery both work. |
| 5 | F04: physical ingress enforcement, then F07 classification | Correct-medium traffic works; cross-medium traffic cannot prove a pair/operation; incompatible and unreachable are distinguished. |
| 6 | F05: coordinated advanced workflows and caller/documentation cutover | Real rendered workflow and migrated drivers require no manual matching or companion HTTP coordination. |
| 7 | F06: bounded candidate-liveness hardening | Improved dead-boot scenario with unchanged proven-session/replay invariants. |
| 8 | G01: final isolated-medium hardware matrix | Retained two-ended state/output evidence for all boot, restart, role, replay and recovery scenarios; independent outdoor gate remains explicit. |

**R06-R closes only when its findings have repair evidence and the applicable acceptance gates have recorded outcomes.** Any intentionally deferred item must remain explicitly open with its risk; passing the existing core suite, publishing this document or flashing a version is not closure. No implementation or deployment is claimed by this documentation checkpoint.
